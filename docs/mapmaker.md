# Mapmaker (added content): architecture and contract
Owner's direction (2026-11-05): Phase 1 is a Godot editor plugin; Phase 2 an in-game Forge-style editor; both run on **one shared core**
("Both editors must share underlying functionality rather than becoming two separate mapmaking systems"). Agentic use is a first-class
requirement: every edit is an operation an agent can run headless through `smtool map`, with the same validation as the editor.
The Mapmaker is **added content** (`docs/added-content.md`): `faithful-build.cmd` builds and ships none of it.

## How to make a map in 2 minutes (play-test flow, 2026-11-17)
The Mapmaker now goes from "I want a map" to "I am playing it with bots" in two presses. The dock's tabs follow the work, left to right: **Map**, **Library**, **Build**, **Object**, **Prefab**, **Test**; the mouse tool and Undo are in a bar above the tabs and **Play test** is always at the bottom (layout: `docs/mapmaker-layout-proposal.md`). The 2-minute guide is the tooltip of the Map tab's hint line.

**Typed transform entries (Object tab, owner 2026-11-18):** Position, Rotation and Scale typed in the Object tab apply to exactly the selected objects. A selected child turns on its own, its parent untouched. When a selected object has a selected ancestor (a parent with all or some of its children selected), only the topmost selected object gets the entry (`TransformTargets.Roots`) and the others follow through inheritance, keeping their relation to it, the same as Godot's multi-select rotate; nothing is turned twice and nothing unselected is touched. With several objects selected the entry is the change to the first one's values, applied to each target.
1. **Open the editor**: `mapmaker.cmd` (builds, opens Godot on `mapmaker/`; the dock is on the right).
2. **Map tab > New map.** Type a name if you like, pick a layout (Two-base arena is the default), press **New map**. The map appears, is saved to your maps folder at once and is checked.
3. **Play test.** Choose a mode and how many bots a side on the **Test** tab (the defaults are fine), press **Play test** (the button at the bottom of every tab). It saves, builds, starts a server on this PC only (127.0.0.1, with the F6 dev tools), starts the bots and opens the game on your map. Close the game window to stop everything. In a checkout it builds first (`tools/mapmaker-playtest.ps1`); in the tester install it runs the installed build's server and game (`mapmaker\playtest.ps1`, no building; the launcher's MAPMAKER button tells the editor which build, and a missing game file is named in the status line).
That is **2 presses** from a started editor (3 with a name typed). To change the map first:
- **Build tab**: click a piece (Floor, Wall, Cover block, Ramp, Column, Invisible wall, Marine or Chaos spawn, spawn door, Capture point, Kill zone), then click in the 3D view. It lands where you click, on the floor or on top of a block (stacking), snapped to the grid, with a sensible default size; spawn areas and doors face the middle of the map. Right click or Esc stops placing.
- Move with the editor's gizmo (W move, E turn, R size) or type numbers in the **Object** tab (Scale is the size in metres; for a piece, Position is the middle of its footprint on the ground; Rotation Z turns it). Ctrl+D duplicates, Del deletes, Ctrl+Z undoes (every step).
- **Check list** (Test tab, updates after every edit, in plain words): what is missing or broken, with a **Fix it** button for the common ones (no spawn for a side, no capture point, no door, no floor) and **Select** to find the object. The bots' route is checked on the real walking graph only when you press **Check route** (owner 2026-11-21: building the graph takes every core for seconds, and running it after every edit pinned a tester's CPU at 99 % once both spawn areas stood on floor).
- **Game modes** (Map tab; the modes this map is for): tick Annihilation, Seize Ground, or both; any combination, at least one (the file keeps names this version does not know, for future modes). Each ticked mode is checked: Seize Ground needs a capture point; Annihilation needs a spawn area for each side.
- **Share**: the `.smmap` file is the whole map. Send it; the other person puts it in their maps folder (`%LOCALAPPDATA%\sm-reimpl\mapmaker\maps`, or any folder named by `SM_MAPS_DIR`) and plays it. Test tab > Share > Show file / Copy path.
Agents and tests: `smtool map new f.smmap --template arena`, `smtool map check f.smmap --text`, `tools/mapmaker-playtest.ps1 -Map f.smmap -Mode seize -Test -OutDir <dir>`.

## Pieces (gameplay)
Objects with `"piece": {"kind": ..., "side": ...}` instead of an asset or prefab (a document has any mix). Position = the middle of the footprint on the ground, scale = size in metres, rotation Z = facing in degrees (0 faces +Y, positive turns toward -X; the same number as an install marker's rotation). Kinds: `box` (solid), `ramp` (solid, rises toward +Y), `column` (solid), `collision-box` (solid, not drawn in the game: put it round decoration), `spawn-area` (side marines or chaos: the start area, spawn spots on a 2 m grid on the floor inside it, players face the area's +Y unless a door gives the room an exit), `blocker` (side: a spawn door, a box the other side cannot cross), `capture-point` (a cylinder: diameter, diameter, height; points are lettered A, B, C in document order), `kill-zone` (anyone inside dies), `move-wall` ("Invisible wall (players only)": a box or, with `"shape": "cylinder"`, a cylinder (scale X and Y the diameter); movement only: stops walking, flying and jumping players of every side, shots fly through it; compiled to `MapContent.Walls`, the same `CollisionWorld.Walls` as Classic's own invisible walls; not drawn in play; the existing `collision-box` stays and is solid for shots too), `cover` ("Cover (shoot-through)": a box, compiled to `MapContent.Props` through the unit box mesh: solid for movement and shots, but a shot with a penetration spec passes it exactly as Classic's baked cover (`BakedProps`); not drawn in play). Pieces are never grouped into prefabs. Operations: `place {piece, visible?, src?, ...}`, `set-piece {id, side?, shape?}`, `set-modes {modes}`, `set-look {sm1Map | null}`.
Layouts (`smtool map templates`): `arena` (22 solid pieces, two walled spawn rooms with doors, a raised middle with ramps, three points), `open-field`, `blank`.
Not in v1 (said so in the editor): pickups (Classic PvP has none to place), lights and sky (the game draws custom maps in a plain daylight look).

## The check (`MapCheck`)
Run on every edit (the route part only on **Check route**) and by `smtool map check`. Errors stop a mode, warnings do not: no ground; no spawn area for a side; spawn area with no floor, or overlapping the other side, or inside a kill zone; no capture point (Seize Ground only); more than 8 points; (warnings) a spawn area under 6 spots, no door, a point with no floor under it, a huge or tiny map. With the install (in the editor when you press **Check route**): the bots' walking graph is built (or read from the cache `%LOCALAPPDATA%\sm-reimpl\cache\nav`) and a route is looked for from each side's spawn to the other and to every point (`no-route` is an error, `point-unreachable` a warning). Falling more than 6 m below the lowest solid piece kills (the map adds a kill floor), so open edges are safe.

## Playing a map (server, client, hash)
- Server: `server.cmd --bind 127.0.0.1 --custom-map f.smmap --mode annihilation|seize` (added content; not with `--map`, `--maps` or Musou). A name that came from the network is never used as a path: it must be `cm_` and plain letters, digits and `_`, and only the search folders are looked in. Files are limited to 8 MB, 20000 objects, 5000 pieces, positions within 100 km and sizes within 10 km (`too-big`). The map's name on the wire is `cm_<name>` (at most 24 letters, digits, `_`).
- Client: told only that name by the server, it finds the file in `SM_MAPS_DIR`, the library's `maps` folder, `maps` beside the program or in the working folder, or is given it with `--custom-map f.smmap`; a missing file gives a plain error naming the folder to put it in. Bots find it the same way.
- The server and every client compile the same file with the same code (`SmMapmaker.CustomMap`): collision (solid pieces, one mesh for characters and shots), start areas, doors, points, kill zones. The handshake's map hash is the first 8 bytes of `SHA-256(canonical JSON of the document + compiler version)`, so a client with a different copy is refused; the collision's own content hash is part of the world's as for every map. **No protocol change, no config-hash change**; original maps are untouched (`BotNavigation.NewMapRules` only adds `cm_` to the maps that get the new-map bot rules).
- Bots: no separate file; each bot builds the walking graph from the compiled collision like on any map (cached by content).

## SM1 pieces in play (owner's decision, 2026-11-19; branch `claude/mapmaker-sm1-in-play`)
Every SM1 placement (`asset.source = "sm1"`, with or without `part`), every part of a prefab instance (prefabs of SM1 parts and imported glTF) and every imported model is **drawn and solid** in a match, each machine using its own install and library. Nothing original is stored in the map, the repo or a build; scenes live in memory (client: with textures; server: meshes only, `MapScene.Read(..., onlyDefinitions, textures: false)`).
- **Compiler** (`CustomMap.Compile(doc, CompileOptions?)`, `DecorGeometry`): objects are unfolded in document order (prefabs from the file's embedded definitions first, the library second; overrides at the top level only, as the editor does); hidden objects and parts are neither drawn nor solid. An SM1 placement's parts are `Sm1Geometry.DrawnVisuals` (the client's default rule: `MapScene.DrawnParts`, highest LOD per family plus uncovered members on the ten imported Classic maps; one part when `part` is set); their triangles (skipping `sky_*` materials: a sky surface is **visible but not solid**, owner 2026-11-20; a definition whose surfaces are all sky, such as `seq_07_sky`, adds no collision and raises no problem; `empty-sm1-definition` stays for a definition with no triangles that is not all sky, `Sm1Geometry.AllSky`; the sky is still drawn by the client's `MapView` rule: from its texture around the camera on maps other than Manufactorum) are placed by the placement's world matrix and added to the one character-and-shot mesh with the pieces. glTF models: `GltfGeometry` reads the same file Godot draws (float POSITION, indexed or not, strips/fans, node transforms, glTF Y-up turned to the document frame); beyond what it supports (Draco/meshopt, sparse, quantised) it refuses by name. The kill floor is under the lowest solid triangle.
- **Collision mode of a prefab** (`collision`): `mesh` = the meshes above. `original-cut` (prefabs extracted from one SM1 map): the original map's own collision triangles (`MapContent` character layers, read from the install) clipped to the prefab's box plus 0.25 m (ours), moved with the instance; its meshes are drawn and not solid. A prefab without one SM1 map as provenance falls back to `mesh` with a note. Overrides that move or hide parts of an `original-cut` instance change only what is drawn (a note says so).
- **Bit-identical on every OS** (`DetMath`). The Linux server and the Windows clients must build the same collision, **all of it**: the solid pieces (boxes, ramps, cylinders), the marker positions and facing, and the decoration. Every vertex (pieces; SM1 blocks; glTF; original-cut copies; parent chains, prefab parts, glTF node transforms, and the SM1 node transforms, which `MapScene` also rebuilds from the raw node data into `VisualPart.DetNode` with `DetTransform`, a new path that leaves `MapScene.Transform` and the Classic maps unchanged) is placed in `double` with rotation angles snapped to 1/1000 degree and a sin/cos made only of IEEE + - * / (argument reduction to a quarter turn and a Taylor series), never the platform's libm or a float matrix routine, and then rounded to 1/4096 m. Cylinder rings use the same sin/cos; a marker's facing is the sum of the snapped Z turns of the object and its parents (no Atan2); a marker's position is its matrix translation on the grid and its size the row lengths. A component that is not finite, a result beyond 1,000,000 m, or a matrix that overflows a float is refused (`bad-transform`; a piece is left out with a note). The grid point is exact in a float only up to about 4096 m; beyond that the cast rounds, still deterministically. The unit tests pin the sin/cos bit patterns and the tolerance against `Math.Sin`.
- **Hash and versions.** `CompilerVersion` 7 (7: edited piece shapes, see "Edit mode contract"; 6: the `move-wall` and `cover` pieces fill the content's `Walls` and `Props`, and the document's `look` is hashed; every custom map's hash changed, so the server and every client must run the same build). A map with decoration hashes the document **and** a SHA-256 of the **source data** of its triangles (`DecorResult.Digest`: each used mesh block of the install, each model file, the original collision, and each prefab that only this PC's library holds); a client or server whose install, models or library differ gets another hash and the handshake refuses it. A map of pieces only hashes the document as before. **No protocol change, no config-hash change** (the VM servers need the install, which they have; deploy the new server build before serving a decorated map: an old server would compile it as graybox and be refused by new clients on the hash).
- **Hostile files.** Embedded prefabs that contain themselves are refused when the file is read (`prefab-cycle`); the walk is iterative with one state shared by all prefabs (5000 prefabs cost one visit each) and nesting beyond 17 levels is `too-big`; library prefabs are checked at compile the same way, once over everything the objects use; the depth limit gives the same answer in any order of listing. Budgets over the whole map (100,000 unfolded prefab parts, 10 million vertices, 10 million triangles, original-cut copies included, glTF files 64 MB, 12 million indices, 20,000 primitives; checked before anything is allocated) refuse with `too-big`; any other exception from the compile (out of memory, a number out of range, bad JSON) is a clean refusal on the server (exit 2), the client and the tools. A definition with no triangles is refused (`empty-sm1-definition`). Collision is two-sided, so mirrored (negative scale) placements need no winding flip.
- **Refusing.** Play and tools compile strictly: a missing install (`missing-install`), a map the install lacks (`unknown-map`), a definition or part it lacks (`missing-sm1-definition`), an imported model not in the library (`missing-asset`, models are not saved in the map file: copy the model folder), a prefab neither embedded nor in the library (`missing-prefab`) or an unreadable model (`bad-asset`) stop the load with a plain message, on the server (exit 2) and in the client.
- **Editor.** The compile is lenient (`EditorScenes`: its loaded maps; an unloaded one is left out), and its problems are check **errors** (`decoration-missing`), so the editor never says ready while play would refuse. It never runs on the main thread: `Compiled()` compiles the pieces at once and a `DecorWorker` builds the decoration in the background (about 400 ms after the last edit, the latest edit wins, a stale result is dropped, disposed with the plugin); the check shows "checking..." until it lands, and `Compiled(wait: true)` (tests, hashes) builds it now. The last decoration is kept in a `DecorCache` (keyed by the non-piece objects, the pieces that are their parents, the embedded prefabs and the loaded maps; builds run outside its lock), so dragging a piece or a spawn area does not triangulate again. Play test and Save use the strict file compile.
- **Drawing** (`CustomMapDecor`, client): one `MapView.Build` per source map over a synthetic scene (a placed object per placement, a definition per definition-and-part holding the compiler's parts), so models, materials, mirroring and instancing are the Classic renderer's; the original map's void floor, decals and lights are not taken. glTF models are loaded with `GltfDocument` as the editor does.
- **Measured** (tester-shaped map from the real install: 164 SM1 placements from mp_tdm_17, mp_dlc1_map2 and mp_tdm_09, 34 prefab instances, 267 drawn placements, 67,009 triangles): compile about 2.5 s (server, meshes only, three maps read); client load worker 5.5 s with textures, decoration nodes built in 0.21 s; `smtool map check` including the bots' route 9.8 s. Generated by `RealInstallFixtureTests` (needs the install; `SM_FIXTURE_OUT` keeps the file; never committed).
- Known limits: a mesh that the original draws one-sided is solid from both sides; thin or non-collidable decoration (cables, cards, grass) is solid too (the owner's rule: drawn means solid); the Classic hide lists (`SmContent.MapDecorLists`, also applied by the headless SM1 import since S2) do not apply to placed pieces; dragging an SM1 placement in the editor still compiles in the background (about 2 s of CPU on a big map).

## Rules
- **Original assets never touch disk.** SM1 meshes, textures and materials are streamed from the install in memory. `.smmap`, `.smprefab`,
  `.tscn` and library files hold only references (map, definition and object names) and transforms. Tests check this.
- **Library** (private, outside the repo): default `%LOCALAPPDATA%\sm-reimpl\mapmaker\` (`maps/`, `library/prefabs/<id>.smprefab`,
  `library/assets/<id>/` with the imported file + `asset.json`, `library/index.json`). Override: `--library <dir>` / plugin setting.
- **Determinism:** canonical JSON (UTF-8, LF, 2-space indent, properties in a fixed declared order, floats as shortest round-trip
  `R` text, invariant culture). The same operations on the same document give byte-identical files, CLI or editor.
- **Stable ids:** objects `o<N>`, from the document's `nextId` counter; never reused. Prefabs and assets: lowercase slug ids chosen at creation.
- **No transform drift:** transforms are stored as components (position m, rotation Euler degrees X/Y/Z in `MapScene.Transform` order,
  scale), never as composed matrices. Edits set components; deltas apply to components. SM1 placements decompose once at extraction.
- **Frame:** documents use the SM1 source frame as `MapScene` produces it, so extracted pieces keep their exact relationship. Views apply the
  same conversion the client's `MapView` applies.

## Document model (`.smmap`, formatVersion 4 (4: piece `mesh` and `material`, map `materials` and `images`, see "Edit mode contract"); version 1 to 3 files are upgraded on open, see "Older and shared map files"; the optional top-level `prefabs` array holds the embedded prefab definitions)
```json
{ "format": "smmap", "formatVersion": 1, "name": "My map", "nextId": 4,
  "objects": [ { "id": "o1", "name": "crate", "parent": null, "layer": "default", "visible": true,
                 "transform": { "position": [0,0,0], "rotation": [0,90,0], "scale": [1,1,1] },
                 "asset": { "source": "sm1", "map": "mp_tdm_09", "definition": "<O3d name>" } },
               { "id": "o2", "name": "bay", "prefab": "manufactorum-bay", "overrides": [], "transform": {...} },
               { "id": "o3", "name": "statue", "asset": { "source": "custom", "id": "my-statue" }, "transform": {...} } ] }
```
An object has exactly one of `asset` or `prefab` (or neither: an empty group). `parent` nests objects; transforms are local to the parent.
An SM1 `asset` may add `"part": N` (index into the definition's nearest-LOD parts) to draw one part only. SM1 bakes much of a map into a few
composite placements (Manufactorum's `tarmacgroundplane` holds the floor, factories, gates and generator buildings in 48 parts), so the editor
picks such placements part by part (ours: 8 or more parts, or wider than 40 m) and names a part by its SM1 node (e.g. `CFactory_Gate`).
The part index follows `ObjectDefinition.NearestLod()`, itself a provisional rule: if that rule changes, saved part indices may point at other parts
(the prefab part's name keeps the node name, so a mismatch can be spotted).

## Prefab (`.smprefab`, formatVersion 1)
`{ format, formatVersion, id, name, tags[], origin:[x,y,z], collision: "mesh"|"original-cut", parts:[{ id:"p1", name, asset, transform }],
provenance:{ source:"sm1"|"custom"|"mixed", map?, objects:[names] }, bounds:{min,max} }` (bounds when known).
Prefab parts can be SM1 or custom assets, or other prefabs (`prefab` instead of `asset`; cycles rejected).
Linked instances: an object with `prefab` draws the master; `overrides` (Phase 1: per-part `visible` and `transform`) survive master edits
while the part id still exists; overrides of removed parts are dropped with a warning.

## Custom assets
`import-asset` copies a glTF 2.0 file (`.glb`, or `.gltf` with its buffers and images) into `library/assets/<id>/` and writes `asset.json`
`{ id, name, file, bounds, sha256, importedFrom }` (bounds from the POSITION accessors' min/max with node transforms). `import-prefab` copies
a `.smprefab` into the library after validation (unknown asset ids are errors).

**Import from Quixel / Fab (no prompts).** Drag a `.zip`, `.fbx`, `.glb`, `.gltf` or an unzipped folder onto the Library list or the 3D view, or use
"Import asset" / "Import folder" (a map must be open). Core (`ModelImport`, tested without Godot): zip extraction with a zip-slip guard (no `..`, no
rooted or drive paths; at most 20 000 entries and 2 GB unpacked, counted while unpacking, not from the headers) and only models, images and `.bin`
files are unpacked; the model is chosen by lowest LOD (`_LOD0`; a name with no LOD counts as 0), then `.glb` over `.gltf` over `.fbx`, then the
shallowest and first path (variation folders resolve to the first). Plugin (`AssetImporter`): loads FBX with Godot's runtime FBX reader and glTF with
`GltfDocument`, turns Godot's `ImporterMeshInstance3D` nodes into real `MeshInstance3D` nodes (see "Why previews and bounds were empty"), builds a
material from Megascans / Fab / Unreal texture names for surfaces that have no albedo picture (Albedo/BaseColor/Diffuse/BC, Normal/N, Roughness,
Metalness, AO, ORM, Opacity into albedo alpha, Emissive; Displacement/Height ignored; a normal map named DX/DirectX gets its green channel flipped,
GL/OpenGL not, and an unmarked Megascans-style `<id>_4K_Normal` is read as DirectX per the owner's note: **ours, a refine item**; textures above
2048 px are scaled down), guesses the unit (a model whose largest side is over 30 m is read as centimetres, x0.01, or millimetres, x0.001; ours),
measures the bounds from the loaded meshes and writes one self-contained `.glb`, which `import-asset` stores. `import-asset` also takes optional
`bounds` (min/max in the glTF frame; wins over the accessors), `from` (the source name) and `import` (free-form record kept in `asset.json`: source,
format, model, lod, scale, units, textures, normalGreenFlipped, sourceSha256). The same download dropped again is recognised by `sourceSha256` and not
imported twice. Draco and meshopt files are refused at import with a message (`unsupported-compression`); other failures are named in the dock status
and an editor toast ("Imported Rock (scale 0.01 (centimetres), 3 textures, LOD0)").

**Why previews and bounds were empty.** (1) Godot's runtime glTF/FBX reader returns `ImporterMeshInstance3D` nodes, which never draw in a running scene,
so every custom asset loaded to nothing and its box stayed empty; they are now converted. (2) A glTF whose POSITION accessors lack min/max has unknown
bounds, and one such primitive discarded the box of the others; the editor now measures the loaded mesh when the library has no box. (3) Draco and
meshopt files load as nothing. (4) The library list requested pictures only for the first 60 rows and capped SM1 definitions at 400; every row is
now rendered lazily (rows in view first, the rest in the background). (5) A part that failed or an empty model was skipped silently; it now shows a
placeholder tile that names the reason (`no mesh`, `load failed`, `map not loaded`, `no geometry`, `empty prefab`, `missing asset`, `unreadable`) and
is logged once. (6) A picture of a prefab whose SM1 map was not loaded yet was cached with holes; it is a placeholder until the map loads, and the
cache file name now carries the content (asset hash, prefab text plus its assets' hashes) and a render version, so changed content is drawn again and
the old file is deleted. (7) SM1 definitions that Manufactorum's armoury rule hides (`MapDecor.Hidden`) built to nothing; they are drawn for the
library under another name. Definitions with no visual part at all (markers, lights, child-only groups) are counted under the list, not listed.

**Extracted single part (owner's report 2026-11-18).** A prefab made from one picked part of a composite SM1 placement (for example one generator block of `tarmacgroundplane`) stores `asset.part`, and every view of it (thumbnail, ghost, placed instance) now draws that part alone (`ContentFactory.BuildSm1Part`). The old build copied the whole definition with `with { Visuals = ... }`, which kept its cached `HighestLod()` list and so drew every neighbouring part. The core's bounds and the extract origin already used the part's own box. Checked by the selftest ("the part prefab draws only that part") and `--mm-libtest` (1 of 48 instances). The game's custom-map view draws graybox pieces only, so it never drew SM1 parts.

**Rename.** Custom assets and prefabs: F2, double click on the name, or right click "Rename..." in the Library list (Enter confirms, Esc cancels). Only
the display name changes (`asset.json` / the `.smprefab`); the id and folder stay, and maps and prefabs refer to the id, so they keep resolving. The name
is trimmed with inner whitespace made one space, 1 to 80 characters, no control characters; a name another item of the same kind already has is
rejected (`duplicate-name`, compared without case; an asset and a prefab may share a name). Not undoable. SM1 definitions are read-only.

**Group to prefab keeps every part where it was** (owner, 2026-11-18). The prefab's part transforms are the parts' world transforms relative to the chosen origin and the replacing instance sits at that origin with no rotation or scale, so every part's world position, rotation and scale is unchanged (any origin; tested with rotated, scaled and offset parts). The one case that used to shift parts: an instance with part overrides (moved or hidden parts) lost its overrides when grouped, so its parts jumped back to the prefab's own places. ## Nesting and groups (owner's pass 3, 2026-11-19)
Two ways to hold objects together, both in the file, both undoable.
**Nesting** is the `parent` field: a child's transform is local to its parent, so it follows when the parent moves. Any object can be the parent of any other, whatever
their kinds (assets, prefab instances, pieces, empty objects); the compiler and the play test read the nested world transforms. The Scene tab's Objects list (drag a row onto
another to nest it, onto empty space to unparent; **Make child of...**, **Unparent**) and a drag in Godot's Scene dock all become `set-parent` operations, which keep the object's world
position and refuse cycles. (The editor's own history keeps its entry for a Scene-dock drag too; undo that step with the Mapmaker step above it first.)
**Groups** are an editing aid with no transform and no effect in the game (the compiler never reads them): a named set of objects and smaller groups, saved in the file as an
optional top-level `"groups": [ { "id": "g1", "name": "Gate", "members": ["o1", "o2", "g2"] } ]` (written only when there are groups; `formatVersion` stays 1 and a file
without the key opens as before; a file that lists a missing object or lists a member twice is repaired on open, not refused). An object or group is in at most one group, so groups
form a tree. Clicking an object selects only it (it moves alone); clicking a group row in the Scene tab selects every object in it, as does a double-click on a member in the 3D view
(again, soon after: the group around it); any mix of selected objects moves together with the gizmo. Actions: New group from selection (whole groups in the selection become one
member, so selecting two groups and grouping nests them), Rename, Add selected, Remove selected, Ungroup, Delete group (objects stay); dragging an object onto a group row adds it.
Test aid: `godot.cmd --windowed --editor --path mapmaker -- --mm-groups --mm-out <dir>`.

## Classic link (format 3; owner's decision 2026-11-20 "import as Classic plays it", slice S1: format and compiler only)
The first slice of making an imported SM1 map the one Classic PvP plays. The file format 2 -> 3 (identity upgrade step; an older Mapmaker refuses a version 3 file with its "made by a newer Mapmaker" message) adds two optional things:
- **`src` on an object (editor only).** `{ "map": "mp_tdm_09", "key": "<stable id of the item in that map>", "fp": "<fingerprint of what it was>", "kind": "placement|wall|kill|cover", "classicHidden": true }`: where an imported object came from, so
  a later "Refresh from Classic" can tell new, changed and removed items apart, and whether Classic hides it (the object is then imported switched off, `visible: false`). Like `grid`, it is left out of `MapDocument.ToGameJson()`
  (`MapObject.ToNode(editorOnly: false)`), so it never changes the map's hash or the decoration cache key; it lives on the object record, so clones, `CopyDocument` and undo keep it. A malformed link is dropped when the file is read
  (repaired, never refused). `duplicate` makes a new object without a link; `place` accepts `src` (a bad one is refused) and `visible`.
- **`look` on the map (game-visible).** `{ "sm1Map": "mp_tdm_09" }`: the Classic map whose lighting, sky, fog and decals play draws the map with (slice S4: the client draws it, see "Look in play"). It is in the hash. The name is `mp_` plus lowercase letters, digits and `_` (at most 44
  characters); a bad one in a file is refused (`bad-file`), in `set-look` it is `bad-op`; `set-look {sm1Map: null}` clears it.
New piece kinds (see "Pieces (gameplay)"): `move-wall` (shape `box` or `cylinder`, written by `place {piece: {kind: "move-wall", shape}}` or `set-piece {id, shape}`) and `cover`. `kill-zone` is unchanged (imported kill boxes use it) and the generated `cm_kill_floor`
stays beside them. The compiler (`CustomMap`, `CompilerVersion` 6) numbers them `cm_wall_N` and `cm_cover_N` (document order). Not yet in S1: the import itself (S3), the client look (S4), "Refresh from Classic" (S5) and the editor's drawing and buttons for the new pieces (done in S6, see "Editor UI for the Classic import"; until
then the editor lists them from `PieceKind.All` and draws what its generic piece drawing gives). Cross-OS: a custom wall's vertices are built by `CustomMap.WallMesh` with the deterministic maths (`DetTransform.Local`, `DetMath.Ring`; the same box and 16-sided circumscribed prism as `WorldBlocker`) and handed to the collision world through `MapWall.Vertices`/`Indices` (additive; Classic walls leave them null and are built as before), so the wall collision is bit-identical on every OS. Cover counts for the generated kill floor and `SolidCount`; walls do not.

## Refresh from Classic (slice S5, 2026-11-20; the engine-free op; the editor UI is "Editor UI for the Classic import" below)
`refresh-from-classic {map?, preview?, apply?, applyAllUnedited?}` recomputes, for each `src.map` in the document (or only `map`), Classic's placements, walls, kill boxes and cover through `ISm1Source.LoadMap` / `LoadGameplay` and `Sm1ClassicKeys` (the same keys and fingerprints as the import) and diffs them with the objects carrying that `src` link; the diff basis is (map, kind, key). `preview` defaults to **true** (changes nothing). Without an install it refuses with `missing-install`. A source with no gameplay reader for a map leaves walls, kill boxes and cover uncompared (a warning), never "removed". The whole run is one batch, so one undo.
- **Added** (Classic item with no object): a run inserts it into its sub-group (found from where that map's objects of the same kind sit; made, under the import group, when missing; visible placements go directly under the import group). Caps: `MapDocument.MaxObjects`, `MaxPieces` and the 8 MB file limit; what does not fit is listed under `skipped` (`too-many-objects`, `too-many-pieces`, `file-size`) and shows as added again next time.
- **Removed** (key gone from Classic) and **changed** (fingerprint differs, hidden state included): always only listed in a preview. A run applies those named in `apply` (an object id, or `map|kind|key`) and, with `applyAllUnedited`, every one not flagged edited. Applying a removal deletes the object (children keep their world place); applying a change sets Classic's transform, size, shape and visibility and stores the new fingerprint (a placement whose hidden state flipped moves between the import group and "Hidden by Classic"). The result's `applied` says which ran.
- **Edited by you**: `src.ob` (editor only, new optional field of the link, written by the import and every refresh) is a hash of the object's own transform, visibility, piece kind and shape and asset as the import left it (`Batch.StateHash`). A removed or changed object whose present state differs is `edited: true`; `applyAllUnedited` skips it, only an explicit `apply` entry applies it. An object with no `ob` (imported before this slice) counts as edited. Only the object's own local values count (moving its group does not).
- **Owner deletions are remembered**: deleting an object that has a `src` link (`delete`, or `group-to-prefab` with `replace`) adds (map, kind, key) to the document's editor-only `removedSrc` list (top-level, like `grid`: not in the hash, part of the file and of undo, repaired when malformed, kept at most `MaxObjects`). A refresh never re-adds such an item; it lists it under `deleted` and `apply: ["map|kind|key"]` brings it back (and forgets the deletion). Removals applied by a refresh are not remembered, since Classic no longer has the item.
- **Result**: the usual result plus `refresh: {preview, maps, added, removed, changed, deleted, skipped}`, each row `{map, kind, key, name, id, ...}` (`id` is null for added in a preview and for deleted; `edited`/`applied` on removed and changed, `hidden` where it applies, `restored` on deleted, `reason` on skipped). Core tests: `Sm1RefreshTests`.

## Look in play (slice S4; owner's decision 2026-11-20)
A map whose document has `look.sm1Map` is drawn in play with that Classic map's original look, as Classic plays it; without `look` it keeps the plain daylight look (ours). The source map's own geometry is never drawn: the custom map's pieces and imported placements are the geometry.
- **What is drawn** (the same code Classic uses; `client/Extras/Mapmaker/NetworkView.Mapmaker.cs`): the sun, ambient, fog, environment regions, colour grade and placed lights (`NetworkView.ApplyMapLighting`, now shared with the Classic load in `NetworkView.MapLoad.cs`), the sky texture (`MapView.BuildLook`, sky surfaces only; on Manufactorum the sky stays the lighting's background, as in Classic), the level decals, the ortho projector lights and the void floor (`MapView.AddLevelLook`, also shared; the void floor lies 1.5 m under the lowest solid piece). The source scene is read on the load's worker (`ExtrasMapLook`), like Classic's. Decals and projectors keep the source map's positions: they show where imported placements sit at the same place, and project onto nothing elsewhere (estimate).
- **Spinning fans.** Imported SM1 placements of a definition the source map turns with a `BezierCurve` (`MapScene.Spinning`) turn at that rate about their own origin; matched by definition name (`LookCheck.SpinningDefinitions`), so every placement of that definition spins (estimate: Classic spins only the curve-carried placements).
- **Refusal, no fallback.** A PC whose install lacks the look's map refuses the map before it joins: the load stops with "This map uses the look of <map name>, which your game install does not have." (the name from the install's front-end list, else the archive name; `LookCheck`). The join screen, the info overlay and the console show that sentence instead of the server's generic map mismatch. A look map that is installed but cannot be read refuses the same way, with the reason. A lean bot (the default for bots) draws nothing and joins anyway; `--bot-full-load` bots and players check.
- Classic is unchanged: `MapView.Populate` calls the same `AddLevelLook` and the Classic load the same `ApplyMapLighting` (moved verbatim); `BuildLook` is a separate entry with a flag no Classic path sets.

## Grid (owner's request, 2026-11-20; editor only)
The Map tab's **Grid** section (after Snap, before SM1 reference map) configures the reference grid of the 3D view: **Show grid**, **Colour** (with alpha), **Cell size (m)**, **Height (m)**
(SM1 Z, Z up; **From selection** takes the lowest point of the selected objects' boxes, parents, rotation and scale included) and **Draw over objects** (on: no depth test, the grid
shows through pieces; off: pieces hide it). It is independent of the Snap step (`MapHost.GridStep` is untouched).
- **Static.** `EditorGrid` draws one fixed `ArrayMesh` of line segments (unshaded, 1 px GPU lines): lines every cell size metres over a fixed 400 m x 400 m area centred on the origin
  (`MapGrid.HalfExtent` 200 m; cell sizes 0.1 to 100 m, so at most 4001 lines per direction). Nothing about the camera reaches it: no subdivision, no fade. The mesh is rebuilt only when
  the cell size changes. Far away, lines of a small cell size alias (moire) because they stay 1 px: that is the cost of "never changes".
- **Godot's own grid** subdivides with zoom, so it is switched off while a Mapmaker scene is open: every "View Grid" check item of the 3D editor (its View menu and each viewport's menu)
  is unchecked through its own menu (`id_pressed`), remembering which were on; they are checked again when the Mapmaker scene closes or the plugin unloads (`EditorGrid.HideBuiltIn` /
  `RestoreBuiltIn`). Godot re-applies a scene's own grid state a moment after a scene opens, so the plugin repeats the hide for 1.5 s after a Mapmaker scene becomes the edited one
  (`HoldEditorGrid`); a user who switches Godot's grid on by hand later is left alone.
- **Data.** The optional top-level `grid` object of the `.smmap`: `{ "show": true, "colour": "#rrggbbaa", "cellSize": 1, "height": 0, "drawOver": false }`, written only when it differs from
  the defaults (shown, `#80808080` grey 50% alpha, 1 m, 0, off), so formatVersion stays 2 and old files open with the defaults. Out-of-range or odd values in a file are repaired, not refused.
  The grid is not part of the map's game meaning: `MapDocument.ToGameJson()` (the text the map hash covers) leaves it out, so changing it never changes the hash, the compiled
  map or whether two testers can meet. (Groups are still inside the hashed text; unchanged.)
- **Editing.** `set-grid {show?, colour?, cellSize?, height?, drawOver?}` goes through the normal batch, so every edit marks the map changed and is one undo step (a held spin arrow folds
  into one step; the colour picker previews live and makes one step when it closes). With no map open the section is disabled and the defaults are drawn.
- Test aid: `godot.cmd --editor --path mapmaker -- --mm-grid --mm-lib <dir>` (add `--windowed --mm-out <dir>` for two pictures); core tests `GridTests`.

## Edit mode contract (format 4, compiler 7; owner-approved brief 2026-11-25 "Blender-style controls", phase M0: engine-free core)
The shared core every later phase builds on: the editor's Object/Edit mode (M1), the runtime shapes and volumes (M2) and the material editor (M3) call these types and operations, and agents reach all of them through `smtool map`. Added content (`src/SmMapmaker/Extras/`); the neutral volume type `SmSim.MeshVolume` lives in the core simulation (`src/SmSim/MeshVolume.cs`, unused by Classic) so core sim files can use it in a build without added content. Contract v2 (2026-11-25, after the M0 review) is described here.
- **Editable shape** (`EditMesh`, object field `mesh`, pieces only, game-visible): `{ "topology": "box"|"ramp"|"column12"|"cylinder16", "vertices": [[x,y,z], ...], "faceSlots"?: [...] }`. No `mesh` = the stock shape from the scale, exactly as before (old maps load and play unchanged); a mesh equal to the stock shape is written as no mesh (one way to write it, so an edit and its reverse restore the hash). Vertices are in the piece's **unit space** (the object's local frame before its scale: footprint -0.5..0.5, height 0..1, bottom-centre origin); the object's scale still multiplies them, so the Scale fields keep their meaning (Blender's object scale). **Sized space** = unit x scale = metres along the object's own axes: every edit and dimension is measured there.
- **Topologies (frozen; part of the file format).** `box` (block, invisible wall, cover, spawn area, spawn door, kill zone, box players-only wall): the 8 corners of the unit box, faces 0 bottom, 1 top, 2 -Y, 3 +Y, 4 -X, 5 +X (tool names `-z +z -y +y -x +x`, `bottom top front back left right`). `ramp`: 6 vertices, faces bottom, slope, back (+Y), left, right. `column12` (column) and `cylinder16` (capture point, round players-only wall): an N-gon prism inscribed in the unit circle, bottom ring 0..N-1, top ring N..2N-1, faces bottom, top, then the sides. Faces are polygons wound counter-clockwise from outside (a wall face is one face; picking either of its triangles selects it: `Triangulate().TriangleFace`); edge ids are the unique edges in the order the faces first walk them. No extrusion or subdivision, so ids never change. Changing a players-only wall between box and cylinder resets its edited shape (a warning).
- **First edit of a round piece (lead 39 decision).** A round piece's first edit starts from its prism inscribed in the circle: a round players-only wall goes from the 16-sided prism round the circle (circumscribed, its collision) to the 16-sided prism inside it, and a capture point from the circle (X size) to the 16-gon of its X and Y sizes. For a round wall, and for a capture point whose X and Y are equal, the outline moves by at most 1.9 % of the diameter (1 - cos(pi/16)); a capture point with X different from Y also takes its Y size, which it did not use before (it played as a circle of its X size), so its outline can move by up to half the difference. Afterwards the shape is exactly what was edited.
- **Component edits** (`ComponentSelection`, `MeshEdit`, `MeshOps.Apply`, pure): select vertices, edges or faces by id; move (delta in metres), rotate (degrees about an axis, deterministic sin/cos) or scale (factor) the selected vertices in the object's own axes, with an optional axis constraint. Pivot: `selection` (default, the selection's box centre: a face's centre, an edge's midpoint), `median`, `origin` or a point. Only the selected vertices change and the others keep their bits: pulling the +X face keeps the -X face where it was; scaling a column's top face tapers it with the base planted; a vertex two selected faces share moves once. An edit that leaves the shape thinner than 1 cm on an axis is `bad-mesh`.
- **One undoable action** (`MeshDrag`): a drag or a G / R / S + axis + typed value previews from the shapes as they were when it began (`Update` each frame, `Preview`, `Dims`) and ends in `Commit` (one `edit-mesh` batch: one undo step, the same bits as the last preview) or `Cancel` (nothing changed); a document that changed meanwhile gives `stale-edit`. Undo and redo are the session's (snapshot journal, unchanged).
- **Dimensions** (`MeshDims`): the extents of the resulting shape along the object's own axes with its scale applied, so turning a wall never swaps its length and width and a shape edit with the scale fields untouched still reads right; `Label` gives "X 5.00 m   Y 2.00 m   Z 1.00 m". An unedited capture point reads (X, X, Z): it plays as a circle of its X size (the old rule, kept), and the check notes `point-round` when its Y differs.
- **Operations**: `edit-mesh {targets: [{id, mode: vertex|edge|face, ids}] (or id, mode, ids), move: [x,y,z] | rotate: degrees | scale: [x,y,z] or n, axis?: x|y|z, pivot?}` (several objects in one step; each in its own axes about its own pivot) · `set-mesh {id, mesh | null}` · `reset-mesh {ids}` · `image-add {path, name?}` (-> `createdImages`) · `image-remove {id}` (`image-in-use`) · `material-add {name?, nodes?, links?}` (-> `createdMaterials`) · `material-set {id, name?, nodes?, links?}` · `material-edit {id, addNodes?, removeNodes?, setParams?, moveNodes?, unlink?, link?}` (in that order; a link into an occupied input replaces it) · `material-remove {id}` (`material-in-use`) · `set-material {ids, material | null}` (drawn pieces only: block, ramp, column; others `not-renderable`). Codes: `not-editable`, `unknown-component`, `empty-selection`, `bad-mesh`, `bad-graph`, `unsupported-graph`, `unknown-material`, `unknown-image`, `bad-image`, `missing-image`, `bad-pack`, `stale-edit`.
- **Materials** (map field `materials`, game-visible): `{id: "m<N>", name, nodes: [{id, type, params, position}], links: [{from, out, to, in}]}`. Node types: `image-texture {image}` (in vector; out color, alpha), `mapping {scale: [u,v] repeats per metre, offset}` (out vector), `normal-map {strength, convention: opengl|directx}` (in color; out normal), `separate-rgb` (in color; out r, g, b), `pbr-surface {baseColor, metallic, roughness, ao}` (in base-color, metallic, roughness, normal, ao; out surface), `output` (in surface). Sockets join by type; a colour into a float input takes its red channel. Parameters are stored without defaults (one way to write them). `MaterialGraph.Resolve` flattens a graph into one `PbrMaterial` (textures with their channel, scalars, normal strength and DirectX flag, one UV scale and offset): the one description the editor preview and the game both build their surface from (preview = saved = in game). A graph that cannot be one surface (two different mappings, base colour from one channel, normal not from a normal map) is refused when edited (`unsupported-graph`). Object field `material` assigns one; `faceSlots` (per-face slots) is reserved in the format and not drawn yet.
- **Images** (map field `images`, game-visible): `{id: SHA-256 of the bytes, name, format: png|jpg, width, height, bytes}`; PNG or JPEG by signature, size from the header, at most 32 MB and 8192 px a side, 64 a map. The bytes are never in the `.smmap` (its 8 MB limit): `image-add` stages them into `library/images/<id>.<format>` at commit, Save copies every image the map uses into `images/` beside the map file, and opening a map adds images found beside it to the library. `MapImages.Read` returns verified bytes (beside the map first, then the library; a copy whose hash differs is skipped). The hash covers the images through their ids, so client and server agree without the server reading a picture.
- **Sharing** (`MapPack`, `.smpack`): a zip of the `.smmap` and `images/<id>.<format>`; unpacking accepts only those (no other paths, `..` or rooted names; each image's name must be its own SHA-256; size limits counted while reading), refuses a map that lacks one of its images and never overwrites a map file. Contract v2: the map entry's name is plain (letters, digits, space, `_ . - ( )`; no `:` stream names), no backslash or deeper folder, no repeated entry, a file that is not a zip is `bad-pack`; each listed image is read alone and checked against the map's list (SHA-256, format, size), unlisted images are skipped, and the map file is written last and atomically. Images in a map are limited to 64 Mi decoded pixels in all (`MapImage.MaxTotalPixels`); `MapImages.Read` also checks a copy's header against the list; re-adding an image the map already lists writes a lost library copy back.
- **Drawing data** (`DrawPiece.Mesh`, `.Scale`, `.Material`, `.Shape`, `.Render()` -> `RenderMesh`): flat triangles in the document frame with normals, tangents (w = handedness) and UVs. UVs are planar per face in sized space, one unit per metre (pulling a face adds texture, it does not stretch), oriented so pictures are not mirrored and stand upright on walls (ours, provisional).
- **In play (compiler 7).** An edited block, ramp, column or invisible wall collides by its mesh (the same deterministic placement as stock pieces); edited cover is a prop of its mesh (Classic's penetration rule unchanged); an edited players-only wall hands its mesh to `MapWall.Vertices` (movement only, shots pass). An edited spawn area, spawn door, capture point or kill zone gets a record that is its mesh's box along its own axes (centre and full size; a capture point's two horizontal sizes, no longer X twice) and its exact shape in `CustomMap.Volumes` under the record's name: a `SmSim.MeshVolume`: `Contains` is the non-zero winding of a ray straight up (in double, a top-left tie rule in plan, a crossing counted only strictly above), so a self-overlapping shape is inside wherever any part covers the point, the bottom surface is in and the top out, on a box the -X and +Y faces in and the +X and -Y faces out (half-open: two touching volumes never share a point), and a non-finite point is never inside. For the runtime: `Crosses(a, b)` (segment test, the mesh equivalent of `KillVolume.Crosses`, so a fast mover does not pass a thin volume), `InsidePoint()` (a point that is inside, where the box centre may not be), `ReachingAbove(top)` and `PushOut(feet, radius, height)` (the mesh equivalents of `SpawnBlocker`'s), `FeatureEdges()` (outline for a drawn shield or ring) and `Hash(h)` (for a world's content hash). Contract v3: a flat triangle's height is its corners' exactly (so flat bottoms and tops follow the rule at any height and position); `ReachingAbove` keeps the authored shape and adds a closed prism from every upward-facing triangle up to the height (everything straight above the shape is inside; a gap under an overhang of a non-convex shape is filled too); `PushOut` measures to the outline (`FeatureEdges`) only; `Crosses(p, p)` is `Contains(p)`, so unlike `KillVolume.Crosses` a zero-length segment on the top or a +X / -Y face does not cross. An edited marker's record takes its vertical centre and height from the gridded world vertices, so `Position.Z - Scale.Z / 2` is exactly the volume's lowest point (where the compiled spawn stands). For M2: filter start-area spots with a vertical `Crosses` column (as `World.SpotsIn` accepts ground up to 1 m below a spot), and take a spot's XY from an inside floor point (`InsidePoint` returns a mid-height point; drop it to the floor). Same answer on every OS (IEEE + - * / in double only). Wiring the volumes into the simulation (points, start-area spots, doors, kill zones) is phase M2; until then the records' boxes are what play uses. Unedited markers are exactly as before (a capture point still uses X for both horizontal sizes).
- **Runtime rules for M2 (contract v4, settled).** (1) Build each raised door volume once, when the world is made (`ReachingAbove(SpawnBlocker.AboveLevel` top`)`), and keep it; call `Contains`, `Crosses` and `PushOut` on that raised volume (`PushOut` and `FeatureEdges` use its `Authored` shape's outline; draw the shield from that outline up to the raised `Max.Z`). (2) A raised volume is the union of vertical prisms over every non-vertical triangle of the authored shape, so it does not depend on the mesh's winding; every volume is also turned right way out when made (negative signed volume: a mirrored placement or a face pulled through), so an inside-out edited marker still holds its inside. (3) Start-area spots: keep `World.SpotsIn`'s 2 m grid over the record box (centred, turned by its yaw); a candidate counts only when the vertical column at it from the record bottom - 1 m to its top crosses the volume (`Crosses`) at the spot and at the four points 1 m from it along the area's own axes (the edge inset that `SpotsIn` gets from its 1 m margin), and its ground is found as `SpotsIn` finds it. The record centre's XY may lie outside a sheared or non-convex area, so a fallback spot is `InsidePoint()`'s XY with the ground found under it; "drop `InsidePoint` to `Min.Z`" holds only for a flat-bottomed shape. (4) `Crosses` counts a segment that touches a face while `Contains` is half-open, so a vertical column on the boundary two areas share crosses both: test the spot itself with `Contains` after the ground is found if a spot must belong to one area only. Coplanar faces in `FeatureEdges` are judged within 0.5 mm (`MeshVolume.CoplanarTolerance`): the tetrahedron of the shared edge and both far corners is that thin over the larger triangle (6V / 2A), so a tilted cap's thin fan triangles stay one face. (5) The door COLLIDER (contract v4.1): do not hand the raised volume's `Indices` to the character mesh as they are: they are a soup of overlapping prisms whose interior side walls and caps lie inside the solid (harmless for `Contains`, `Crosses` and `PushOut`, but a capsule controller pushes out of every triangle and can snag at the seams where an interior wall meets the surface). Build the per-side door collider from the authored triangles (`Authored.Indices` over the first `Authored.Vertices.Length` vertices) for the shape itself, plus, for the part above it, closed walls from the authored outline (`FeatureEdges`) up to the raised `Max.Z` and a flat cap there (or, for parity with Classic, the raised record box); M2 owns that build and its test. `PushOut` accepts a place only when the column 1 cm past the outline point is clear as well (a leaning face reaches beyond its foot); `ReachingAbove` also raises a shape whose highest corner already reaches the height but whose other parts are lower (up to its own highest point); a NaN or negative radius or height is read as none.
- **Versions.** A document is written in the lowest format that holds it (`MapDocument.WriteVersion`, lead 39 decision): format 4 (an identity step from 3; an older Mapmaker refuses a version 4 file in plain words) only when a piece has an edited shape or a material or the map has materials or images, else format 3, so an unedited map is never rewritten on open and stays openable by the shipped build. Saving over a file in an older format first keeps it as `name.smmap.bak-v<n>` (`MapSession.LastBackup`; never replaced): once per distinct older file, so flipping between format 3 and 4 adds no copies, but a format-3 file changed since its last backup gets a new one (`.bak-v3-2`). `CompilerVersion` 7 changes every custom map's hash, so server and clients must run the same build. Golden pins (`EditContractV2Tests`): the collision content hash and a Seize Ground run of an unedited map, captured before M2 changes the simulation.
- **Tools** (`smtool map`): `edit-mesh <file> <id> (--face +x | --mode vertex|edge|face --ids 1,2) (--move x,y,z | --rotate deg --axis z | --scale f|x,y,z) [--axis] [--pivot]` (and `edit-face`), `dims <file> [ids]`, `mesh <file> <id>` (ids and names of every vertex, edge and face), `script <file> <steps.json|->` (one session: `apply`, `undo`, `redo`, `dims`, `save`, `reopen` steps; there is no undo journal across separate commands), `material list|add|image|assign|resolve|remove <file> ...`, `pack <file> [--out]`, `unpack <pack> [--into]`, `inside <file> x,y,z` (which volumes hold a point, by shape and by box). Tests: `EditContractTests` (the brief's acceptance table at the data level).

## Operations (one JSON object each; a batch is one transaction: all apply or none)

A failed save is rolled back: if writing the library fails midway (disk full, a locked file), every storage step already done is undone in reverse order (assets, trash moves, prefab files, index), the map and its undo/redo stay as they were, and the error names any step that could not be undone. **Play test cannot load another map any more (2026-11-19, pass 3).** Findings: the owner's maps folder holds several files named "My Map" (the dock's default name); before 11-18 the client looked the map up by that name and took the first file alphabetically (an old copy, often the default layout), and a tester whose launcher never finished syncing `mapmaker-project\` (see docs/releasing.md "The Mapmaker", the sync's failure modes) kept the old editor and the old `playtest.ps1` after updating, so the old behaviour stayed. **Older and shared map files (2026-11-19).** `formatVersion` is now 2. `MapUpgrade` (core) holds numbered steps; any older file reads in memory the same way everywhere (one hash for server, client and editor). **Edit controls (2026-11-19).** *Alt box:* with Alt held a left press in the 3D view always starts a selection box (also over objects and on the gizmo) and a release without a drag selects nothing; release Alt for the normal click. *Duplicate* (button, Ctrl+D) puts the copy exactly on the original and selects it. *Spin arrows* (Object and Prefab tabs): right click steps by 10 (position, origin), 45 degrees (rotation), 0.5 (scale); holding an arrow repeats 5 times a second after 0.5 s, one plain step each for the first 3 s, then the step doubles every 1.5 s up to 4096 times (`SpinSteps`). *Group to prefab...* shows a name and id dialog (prefilled "<first object> group") before saving; Cancel changes nothing.

**One component per edit (Object and Prefab tabs, 2026-11-19).** Editing a position, rotation or scale spin box changes exactly that one component; every other component of the object (or prefab part) stays bit for bit as stored, until the owner touches it. The cause of the old drift: every edit rebuilt the whole transform from all nine spin boxes, and a spin box rounds its value to its step (0.01 / 0.1), so rounded copies of the untouched axes were written back. Now `ComponentEdit` starts from the stored transform and replaces the one component; the spin boxes use a 0.001 step (stored precision) and `CustomArrowStep` (0.01 position and scale, 0.1 rotation) keeps the arrow increments; right-click and hold steps are unchanged. Local space is exact. World space: a position edit goes through the parent's inverse and keeps the local rotation and scale exactly; a rotation or scale edit under a turned parent changes the world matrix, so only that property is recovered from the matrix (rounded to 5 decimals) while the other two stay as stored (a non-uniform parent scale with a turn can refuse with `bad-transform`). A multi-selection applies the edited component's delta (ratio for scale) to that component only on each object. Typing in a field is the same. Gizmo drags are unchanged. Note: a Prefab part edit now keeps the selected part (it used to jump to part 1).

*Review fixes (2026-11-19).* Only a rotated parent can couple axes. Under an unrotated parent (translation and axis-aligned scale) a World edit computes only the edited local axis (position: (world - parent position) / parent scale; rotation: the world angle; scale: world / parent scale) and every other value is the stored one, bit for bit. Under a rotated parent the edited property is recovered from the matrix, and any other axis that comes out within 1e-4 of its stored value keeps the stored value (no Euler flips, no extra decimals); moving along one world axis there really does change several local axes. A multi-selection scale edit whose first object's component is below 0.001 sets the typed value on each object as it is (the status line says so) instead of a ratio. Prefab "Apply pivot" shifts only the axes touched since the prefab was chosen; the others stay at no shift.
